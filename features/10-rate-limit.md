# 10. Ограничение скорости исходящих

**Приоритет:** 🟢 низкий · **Трудоёмкость:** S

## Проблема

При первом запуске `imap:pull`/`imap:sentry` на большом ящике все непрочитанные
письма пересылаются мгновенно подряд. Это может: перегрузить эндпоинт-получатель
(всплеск запросов), упереться в его rate-limit (→ 429 → потери без #01), или
выдать подозрительный burst-трафик. Регулятора скорости нет.

## Цель

Ограничивать частоту исходящих вебхуков (N запросов в секунду/минуту), при
необходимости — на каждый эндпоинт отдельно (#03).

## Предлагаемое решение

Использовать `Illuminate\Support\Facades\RateLimiter` в listener:

```php
RateLimiter::attempt(
    key: 'spoon:'.$this->endpoint,
    maxAttempts: config('spoon.rate.per_minute', 60),
    callback: fn () => $this->relay($event->message),
    decaySeconds: 60,
) ?: $this->release($event, delay: 5);   // вернуть в очередь, если уперлись
```

Аккуратнее всего работает в связке с очередью из #01: при превышении лимита
задача переносится (`release`) вместо busy-wait. Для синхронного режима —
короткий `usleep`/`sleep` между отправками как простейший дроссель.

Дополнительно — корректно обрабатывать `429 Too Many Requests` от эндпоинта,
уважая заголовок `Retry-After` (вписывается в backoff из #01).

## Изменения конфигурации

```dotenv
SPOON_RATE_PER_MINUTE=60      # 0 = без лимита
```

## Замечания

- Лучше всего раскрывается вместе с #01 (очередь) и #03 (ключ лимита = эндпоинт).
- Дефолт `0`/высокий — чтобы не замедлять без явной нужды.

## Definition of Done

- [ ] Настраиваемый лимит исходящих в минуту.
- [ ] Превышение лимита откладывает доставку, а не теряет письмо.
- [ ] Обработка `429` с учётом `Retry-After`.

# 01. Надёжная доставка

> 🔀 **Влито в 2.0.0.** Логика надёжной доставки переехала в команду
> `spoon:deliver` (с 3.0 — `mailspoon:deliver`): доставка развязана с чтением,
> ретрай двухуровневый — короткие in-process повторы + backoff между
> запусками через `next_attempt_at`. Отдельная ветка
> `feature/01-reliable-delivery` и синхронный listener больше не используются
> (синхронный ретрай блокировал бы однопоточное чтение).
>
> **Сверка с реализацией (2026-06-12).** Эскиз ниже описывает мир синхронного
> listener'а и целиком вытеснен store-and-forward; маппинг:
>
> - п.1 «проверять успешность перед `markSeen()`» — последовательности
>   «POST → markSeen» больше нет. Маркер (#22) ставится при захвате **после**
>   фиксации в журнале и архиве (исключение при записи = маркер не ставится,
>   письмо перечитается); успешность HTTP управляет статусом записи в
>   `mailspoon:deliver` (`markDelivered`/`markFailed` + `shouldRetry`
>   различает временные и постоянные сбои). Дыра `Http::post()` без `throw`
>   закрыта. Гарантия сильнее заявленной: при долгом провале письмо не висит
>   в ящике, а ретраится из журнала по своему расписанию.
> - п.2 «ShouldQueue + queue:work» — отвергнут: роль очереди играет журнал
>   `relayed_messages` (персистентная очередь с backoff и `max_attempts`)
>   без зависимости от Redis/воркера очереди.
> - п.3 «failed-хук + алерт» — провал фиксируется (`failed` + `last_error`,
>   виден в `--dry-run`), восстановление — `mailspoon:replay --failed` (#15);
>   алерт — остаётся за #07.
> - Конфиг: `SPOON_TRIES/BACKOFF/TIMEOUT` → `MAILSPOON_*` + `MAX_ATTEMPTS`;
>   `QUEUE_CONNECTION` не нужен.

**Приоритет:** 🔴 высокий · **Трудоёмкость:** S–M

## Проблема

В `App\Listeners\NotifyNewMessage::handle()` письмо помечается прочитанным
безусловно:

```php
Http::asForm()->post($this->endpoint, [...]);
$event->message->markSeen();
```

`Http::post()` без `->throw()` **не бросает исключение** на ответах 4xx/5xx.
Значит, если эндпоинт ответил `500` (или `404`, или таймаут на стороне
приложения-получателя), письмо всё равно помечается `\Seen` и **больше никогда
не будет переслано** — данные фактически теряются. `ConnectionException`
(сетевой сбой) исключение бросит, но тогда `markSeen()` не вызовется, а ретрая
тоже нет — письмо «зависнет» до следующего запуска и пойдёт повторно без учёта
причины.

## Цель

Помечать письмо прочитанным **только** после подтверждённой успешной доставки
(2xx) и переотправлять при временных сбоях с экспоненциальной задержкой.

## Предлагаемое решение

1. Проверять успешность ответа перед `markSeen()`:

   ```php
   $response = Http::asForm()
       ->retry(times: 3, sleepMilliseconds: 200, throw: false)
       ->post($this->endpoint, [...]);

   if ($response->successful()) {
       $event->message->markSeen();
       return;
   }

   // не помечаем прочитанным — письмо переедет в ретрай/останется unseen
   throw new RelayFailedException($response->status(), $this->endpoint);
   ```

2. Сделать listener очередным (`ShouldQueue`) с `tries`, `backoff` и
   `retryUntil`, чтобы доставка шла асинхронно и переживала рестарт воркера:

   ```php
   class NotifyNewMessage implements ShouldQueue
   {
       public int $tries = 5;
       public array $backoff = [10, 30, 60, 300, 900];
   }
   ```

   Потребует `QUEUE_CONNECTION=database|redis` (сейчас `sync`) и `queue:work`.

3. После исчерпания попыток — `failed()`-хук: лог + алерт (см. #07), письмо
   остаётся непрочитанным и будет повторно подхвачено `imap:pull`.

## Изменения конфигурации

```dotenv
SPOON_TRIES=5
SPOON_BACKOFF=10,30,60,300,900
SPOON_TIMEOUT=15
QUEUE_CONNECTION=database
```

## Замечания

- Дедупликация (#05) становится важной, т.к. ретраи могут привести к повторной
  отправке — на стороне получателя письма следует различать по `Message-Id`.
- Очередь требует БД/Redis; сейчас `DB_CONNECTION=null`. Для лёгкого варианта
  можно начать с синхронного `->retry()` (пункт 1) без очереди.

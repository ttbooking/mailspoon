# 06. Действия после пересылки

**Приоритет:** 🟢 низкий · **Трудоёмкость:** M (по факту; исходная оценка S
не учитывала store-and-forward)

> ✅ **Реализовано** (после 3.3.1): карта `after` (глобально и на маршруте),
> действия `none`/`seen`/`keyword:<имя>`/`move:<папка>`/`delete`, команда
> `mailspoon:tidy` в расписании. Исходный эскиз «в listener после
> успеха/провала» оказался нереализуем в 2.x+ — см. «Как реализовано».

## Проблема

Единственное действие после доставки — маркер захвата (#22). Письма копятся в
INBOX навсегда. Нет способа архивировать обработанное, складывать ошибочное в
отдельную папку или удалять после пересылки — а это типичные сценарии гигиены
ящика-«робота».

## Цель

Настраиваемое действие над письмом по итогу обработки: пометить, переместить,
удалить.

## Как реализовано

### Конфигурация

```php
'after' => [
    'delivered' => env('MAILSPOON_AFTER_DELIVERED', 'none'),
    'failed'    => env('MAILSPOON_AFTER_FAILED', 'none'),
    'filtered'  => env('MAILSPOON_AFTER_FILTERED', 'none'),
],
```

Маршрут может переопределить любой исход (`routes.{ящик}.after.{исход}`,
каждый исход откатывается на глобальный отдельно). Словарь действий
(`Support\AfterAction`) унифицирован с маркерами #22: `seen` и
`keyword:<имя>` вместо задуманных `mark_seen`/`flag:` из старого эскиза.

### Исходы разнесены по фазам store-and-forward

- **`filtered`** известен при захвате, соединение открыто — действие
  выполняется сразу в listener. Маркер ящика ставится **до** действия: даже
  если действие упало, письмо не будет перечитано.
- **`delivered`/`failed`** наступают в `mailspoon:deliver` без IMAP-соединения
  и, возможно, спустя сутки backoff'а. Их применяет отдельная команда
  **`mailspoon:tidy`** (расписание `mailspoon.schedule.tidy`, по умолчанию
  ежеминутно): выбирает записи журнала с финальным исходом и без `tidied_at`,
  группирует по ящикам, подключается и действует. Без настроенных действий —
  no-op без подключения. Класть это в `mailspoon:pull` было нельзя:
  sentry-ящики pull не выполняют.

### Поиск письма постфактум: UID + верификация

При захвате в `relayed_messages` пишется `uid` (новая колонка). UID стабилен
только внутри эпохи `UIDVALIDITY`, поэтому tidy **сверяет identity**
найденного письма с записью — по `Message-ID`, а при его отсутствии по
fingerprint (sha256 сырого MIME, для этого письмо догружается с телом).
Несовпадение/отсутствие письма (переехало, удалено вручную, сменился
`UIDVALIDITY`, захвачено без UID) — запись помечается пропущенной, чужое
письмо не трогается. Это сознательная альтернатива хранению `uidvalidity` в
записи: не требует `STATUS`-запроса на каждое письмо при захвате и защищает
строже.

### Семантика и крайние случаи

- `failed` = **финальный** провал: `attempts >= max_attempts`. Пока идут
  ретраи, письмо на месте.
- `tidied_at` фиксирует выполненное (или признанное невыполнимым) действие;
  `mailspoon:replay` сбрасывает его вместе со счётчиком — новый исход получит
  своё действие. Если письмо к тому моменту уже переехало (старый UID/папка),
  верификация не пройдёт и запись будет помечена пропущенной.
- Исход без настроенного действия у ящика, где действия в принципе есть,
  финализируется без операции — чтобы не пересканироваться вечно. Ящики
  совсем без действий tidy не трогает и записи не штампует.
- Папка для `move:` создаётся автоматически (`folders()->firstOrCreate()`).
- `delete` ставит только флаг `\Deleted` (без expunge) — дефолты безопасны,
  по умолчанию вообще `none`.
- Действие резолвится в момент tidy (как ключ подписи в момент доставки) —
  смена конфига действует на ещё не обработанные записи сразу.
- `mailspoon:doctor` валидирует и печатает действия по каждому ящику.
- Retention: prune (дефолт 3 дня) не дожидается tidy, но tidy ежеминутный —
  на практике гонки нет. Записи `failed` prune не трогает вовсе (отдельная
  тема, см. #01).

## Definition of Done

- [x] Поддержка `seen` / `move:` / `delete` / `keyword:` (вместо
      `mark_seen`/`flag:` — словарь унифицирован с маркерами #22).
- [x] Разные действия для delivered/failed/filtered; глобально и на маршруте.
- [x] Безопасные дефолты (`none` везде, никаких удалений по умолчанию).
- [x] Тест на каждый тип действия (move/keyword/delete + filtered-фаза).
- [x] Финальность `failed`: ретраящееся письмо не трогается (тест).
- [x] Верификация identity по UID: чужое письмо не трогается (тест).
